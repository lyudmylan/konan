# Order-creation 500s — unguarded null price in create_order

## Summary

Root cause identified. The order-creation handler `create_order` (faultline
`shop.py:82`) computes `total_price = round(product["price"] * order.quantity, 2)`
with no null-price guard; product 4, "Mystery Box", is the catalog's only
`price: null` row (E8), so every order for it raises an unhandled `TypeError` and
returns 500 while orders for priced products succeed — three user failures in the
window, with a successful order landing *between* them on the same route (E3, E4,
E5). The exception message's operand order (`'NoneType' and 'int'`) is load-bearing:
it proves the *price* was None, not the quantity (E2). Process health, chaos state,
and dependency shapes were checked and ruled out (H2, H3 invalidated). Impact is
confined to orders for product 4 while its price is null — and any product whose
price becomes null joins the same failure mode.

## Timeline

All times UTC, from telemetry.

- **08:49:02.915Z** — process start, faultline 0.1.0 (E1); no telemetry exists
  before it.
- **08:49:09–10Z** — two successful user orders, products 1 and 2 (201s with
  `order_created` events; E6 counts them).
- **08:49:12.244Z** — first user failure: `TypeError` at `shop.py:82` in
  `create_order` → `POST /orders` 500, request `c239ec026e1c` (E2, E3).
- **08:49:13.300Z** — second identical user failure (request `4f842a3546a5`).
- **08:49:15.340Z** — user success *between* failures: order 3, product 1 (E5) —
  the write path is alive mid-incident.
- **08:49:16.382Z** — third user failure (E4); last failure in the window.
- **08:49:17.423Z** — last user request (GET /orders → 200).
- **08:49:22Z** — investigation baseline: health green ~5s post-window (E12);
  counters 3×201 / 3×500, `TypeError`=3, chaos 0 (E6, E7).
- **08:50:10–50Z** — lens probes: catalog shows the single null-price row (E8);
  uptime monotonic, RSS flat, durations fail-fast, counters unchanged — all
  failures predate any konan-* probe (E9, E10, E13).

## Investigation

Baseline showed the incident shape immediately: the only 5xx series in the counter
block was `POST /orders` 500=3 against 201=3 on the same route, with
`http_exceptions_total{type="TypeError"}` exactly matching (E6, E7) — a
data-dependent write-path split, on a green health endpoint (E12).

Triage ran three lenses in parallel, blind to each other. Software-defect pulled the
stack (raise site `shop.py:82`, `create_order`) and read the catalog — the only
null-price row is product 4 (E8). Infra-process returned a clean domain: single
startup, monotonic uptime, flat RSS, fail-fast millisecond errors, a 201 served
between the 500s (E1, E5, E9, E10, E13). Interfaces ruled out injection and
intermediaries: chaos gauge 0 with zero chaos events in the complete log, no
502/503/504 series anywhere, stack terminating in local application arithmetic
(E11, E6, E2).

Selection: **no deep-dives**. H1's evidence was already deterministic and complete
from triage — the null price is directly observed in the catalog, the raise site is
named in the stack, and the one remaining link (which product the failing orders
targeted) is structurally unfillable through this surface: POST bodies are not
logged, failed orders emit no `order_created`, and the failing operation cannot be
probed read-only. That is a gap to record, not a query to run. All three hypotheses
went straight to the judge.

The judge (fresh context, cited evidence only) validated H1 and invalidated H2 and
H3, adding refinements adopted here: the operand-order proof (None is the price, by
the exception message), the universality caveat ("every order for it" is
mechanism-supported — three observed instances, none directly labeled product 4),
"priced products succeed" observed only for products 1 and 2, and E12 recast as
post-window liveness (E5 is the true mid-window signal).

Budget: one triage round (3 lenses), zero deep-dives of a permitted three, one
judge — concluded in round 1. Tokens: subagents alone consumed ~151k; the
orchestrator's share is not measurable in an interactive session, so the machine
core records `tokens: null`.

## Hypotheses

### H1 — data-dependent code defect on the write path (validated)

`POST /orders` fails with an unhandled `TypeError` at `shop.py:82`: `total_price =
round(product["price"] * order.quantity, 2)` with a None price. The accounting is
exact — 3 user 500s, 3 TypeErrors, the only exception series and the only 5xx
series (E6, E7); all three failures carry the identical raise site (E2; the 1:1
type-to-500 pairing is forced by the counters). The catalog's single null-price row
is product 4 (E8); successes for priced products interleave inside the failure
window (E5). Failures are fail-fast milliseconds (E13), and all predate any
investigator probe — pure user impact.

### H2 — process instability (invalidated)

Baseline uptime of 19.8s back-computes to the 08:49:02Z start and covers the whole
failure window — no restart is arithmetically possible (E9, E1). Peak RSS is a
lifetime high-water mark at ~48 MB (E10), failures return in 5–11 ms (E13), and a
clean 201 landed between two 500s (E5): instability does not selectively fail one
route while serving it correctly seconds apart with a single deterministic
exception type.

### H3 — injected degradation / dependency / gateway (invalidated)

Chaos gauge 0 with zero chaos-event lines in the complete log (E11) and no
chaos-control traffic in the complete counter block (E6) — no in-band channel by
which chaos was ever on. The stack terminates at a local multiply inside
`create_order`, not a dependency or transport frame (E2), and the only 5xx series
anywhere is the app's own 500 — no 502/503/504 exists to attribute to an
intermediary (E6).

## Safe next steps

Read-only suggestions; remediation is out of scope for this report.

- Hand to the service owners: guard the `total_price` computation in `create_order`
  (`shop.py:82`) against a null `product["price"]` — any product whose price
  becomes null fails identically.
- Ask the data owners whether product 4's null price is bad data or
  unpriced-by-design (gap 6); the answer decides data fix vs orderability guard.
- Observability: failed order attempts log no `product_id` (gap 2 exists because of
  it) — adding the target product to order-failure logs would turn this
  investigation's one inference into a direct observation.
- Watch `http_exceptions_total{type="TypeError"}` (E7): growth means ongoing user
  impact.
