# Routine handover check: shop service healthy, one latent zero-stock defect

## Summary

**No active incident.** The shop service is serving normally right now: health 200, every
catalog and order route answering in 0.4-1.8 ms, the degradation toggle off at both the
baseline and the failure window (E2, E10), one process start and no restart (E3, E4, E15),
and a flat memory footprint (E2, E16). No unstamped request returned a non-2xx status
anywhere on record (E2, E5).

The check did surface a **latent defect**, and it deserves the next shift's attention even
though no user has hit it. `GET /products/{product_id}` divides by `units_in_stock` with no
zero guard, so every request for a zero-stock product returns 500 with a `ZeroDivisionError`
(E7, E8, E9). Product 3 "Unobtainium Ingot" has `units_in_stock: 0` (E6) and fails on every
attempt; the three non-zero-stock rows probed all return 200 (E11, E12, E13). The catalog
listing advertises product 3, so any user who opens it gets a 500 — the defect is one click
away from a real customer, not hidden behind an unusual input.

Two points of honesty about impact. First, every 500 on record carries a `konan-` investigator
request id; the 4 errors and 4 exceptions in E10 are **my own probes**, and no error rate for
users may be read from them. Second, the reason no user has been affected is that no user
asked for a zero-stock product in the window — absence of exposure, not a benign defect.
Confidence in the mechanism is high (the stack trace names the expression, and controls in
both directions agree); confidence that users are unaffected extends only to this process
life.

## Hypotheses

### H1 — zero-stock division by zero on the product detail route — **validated**

`turnover_score = units_ordered / product["units_in_stock"]` at `shop.py` line 64 throws when
stock is 0 (E8), the exception surfaces as a 500 on `/products/3` (E7) under the same request
id as the access line (E9), and the exception counter carries only `ZeroDivisionError` with a
count equal to the 500 count (E10) — so every failure on record is this one mechanism. Both
directions are now tested: 500 on the zero-stock row, 200 on stock 119, 75 and 500 (E12, E11,
E13). The list route stays 200 (E6) because the score is computed only on the detail route.
Nothing argues against it. Two narrowings hold: "unhandled" is loose — a global trap returns
structured JSON and increments a counter, so the exception is uncaught at the call site rather
than unhandled by the app; and "product 3 is the only affected row" is true of the catalog as
observed (E6), not guaranteed forward.

### H2 — no unstamped request failed in the window — **validated (as scoped)**

This rests on evidence of absence, not absence of evidence. Unstamped traffic ended at
06:36:41.143 (E5); the baseline scrape at 06:37:17 therefore already counted all of it and
shows no non-2xx series at all and an exception counter with no series (E2). The counts close
arithmetically: 2+1+3+2+1 = 9 unstamped requests plus my one health probe = the 10 requests in
E2. Every later 500 is investigator-stamped (E10). The claim is deliberately worded as "no
unstamped request returned non-2xx", not "users are fine": no user asked for a zero-stock
product, so exposure was never tested.

### H3 — degradation switch or configuration change — **invalidated**

Refuted on positive readings, not silence: `faultline_chaos_enabled 0` at the baseline (E2)
and again inside the failure window (E10). The failures are fully explained by a directly
observed mechanism (E8) with controls succeeding on the same route in the same seconds, so no
residue remains for a switch to explain. No config or flag marker appears in the log.

### H4 — crash, restart, hang or saturation — **invalidated**

Uptime readings of 43.0, 46.0 and 155.5 s (E1, E2, E16) are monotonic and all back-solve to
the single start marker at 06:36:32.028 (E4) — a restart would reset the counter. Hang is
refuted by 1.4-1.8 ms responses throughout and a 200 on health *after* all four 500s (E15). Saturation is the weakest clause and is not claimed firmly: two RSS samples
49,152 bytes apart (E2, E16) cannot show a trend and no ceiling is published. The real
refutation is the failure signature — saturation does not fail one product id deterministically
while the next request on the same route succeeds in 1.5 ms.

### H5 — undeclared 500 status and exception-class disclosure — **validated (observable facts)**

The published schema for the route declares only 200 and 422 (E17), and the error body carries
`exception_type: "ZeroDivisionError"` (E7). Two qualifications: a generated schema omits 5xx
for every route by default, so the undeclared status is weak on its own — the disclosure in
the body is the finding; and the body exposes the class name and request id only, with the file,
line and stack staying in the log (E8), so this is not a stack-trace leak. Whether the field is
unconditional or debug-gated is a gap.

### H6 — null price as a fault — **invalidated**

A positive counter-test: the exact row on the exact route returns 200 with `turnover_score`
computed (E11), all four 500s are `ZeroDivisionError` (E10), and product 4 holds
`units_in_stock: 75` (E6) so it cannot reach a zero denominator. It stays a data-quality
anomaly: no order line references product 4 (E14), so order arithmetic against a null price has
never been exercised, and konan cannot exercise it read-only.

## Safe next steps

Read-only suggestions; remediation is out of scope for a journal.

1. **Hand the zero-stock defect to the owning team as the one open item from this check.** The
   decisive detail for them: the division at `shop.py` line 64 (E8), triggered by
   `units_in_stock: 0`, on a product the catalog listing advertises (E6).
2. **Settle the blast-radius question**, which this check could not: does `POST /orders`
   decrement `units_in_stock`? If it does, any product can be ordered down to zero and become a
   new trigger, which turns a one-row curiosity into a recurring failure. The answer is in the
   order-handling code, not in telemetry.
3. **Watch for unstamped 500s on `/products/{product_id}`** as the signal that a real user has
   reached the defect. Any non-2xx with a hex (non-`konan-`) request id is the thing to alert on.
4. **Ignore the current error counters for trend purposes.** The 4 errors in E10 are investigator
   probes; a dashboard reading them as user impact will mislead the next shift.
5. If the exception-class disclosure matters for this service's exposure, **check whether
   `exception_type` is debug-gated** in the global error handler — a source question, outside the
   investigator's surface.
