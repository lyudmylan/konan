# konan benchmark — protocol (v1, pre-registered)

The scorecard in `eval/scorecard.md` is a regression gate: five scenarios, single runs, one
model, pass/fail. This document defines the benchmark on top of it — the same
deterministic scorer, but with spread, repetition, contamination control, and models
compared with everything else held constant. It is written before the runs so the
table cannot be shaped after them. Results are generated by `eval/bench.py` from the
committed run directories under `eval/runs/` and summarized in the README.

## The question

With the methodology (skills) held constant, how well does each model investigate —
correct verdicts under attribution pressure, no invented incidents, evidence-cited
claims — and at what cost in tokens and time?

## What is measured

Per investigation (one fixture, one model, one repetition), the scorer semantics of
`eval/README.md` apply unchanged:

- **Passed** — verdict matches, class matches when a root cause is expected, every
  `must_claim` hits, no false attribution, and the journal is citation-compliant.
- **Root-cause accuracy** — over runs whose fixture expects a root cause.
- **False attributions** — on root-cause-identified journals: the cause id differs from
  the fixture's expected cause (journal contract v2), or a `must_not_claim` hits (v1).
- **Citation compliance** — schema + referential integrity (no citation, no claim).
- **Tokens** — the whole run, subagents included: input + output + cache-read +
  cache-creation, from the harness envelope's `modelUsage` (`.meta.json` sidecar; the
  same number is stamped into the journal's `usage.tokens`).
- **Wall clock** — the harness's `duration_ms` for the headless run (no human pauses);
  the journal's own `wall_clock_seconds` (the investigator's stamps) is kept as written.
- **API-equivalent cost** — the envelope's `total_cost_usd`; on a subscription the
  marginal cost is flat, this is the number an API-billed deployment would pay.
- **Quota share** — two measures, both on the subscription (the only meter konan is
  designed for; benchmarks never move to API credits): (a) investigations completed
  between consecutive quota stops per model, from the run sidecars (`eval/bench.py`,
  "Quota" section — a proxy for investigations per 5-hour window; exact only when a batch
  starts near an empty window with nothing else on the pool); (b) `/usage` read by the
  operator right before and right after a single-model batch — the per-model weekly
  percentage delta ÷ runs = the exact quota cost of one investigation on the plan.
  Recorded in the results section with the plan tier.
- **Headless denials** — tool calls that would have prompted and were auto-denied
  (compound commands outside the pre-approved shapes): a proxy for how much of a
  model's idiom the boundary absorbs.

Aggregation (`eval/bench.py`): per **tier × model** and per model overall — pass rate,
root-cause accuracy, false-attribution count, citation rate, medians of tokens, wall
clock, cost, denials. Failed runs (error, no journal, frozen session) count as failed —
never dropped.

## Corpus and tiers

Tier is the scenario id prefix: `t2-` = tier 2, `t3-` = tier 3, everything else = tier 1.

- **Tier 1 — single cause, evidenced** (corpus v1): D1, D2, chaos error-rate, chaos
  latency, healthy baseline.
- **Tier 2 — attribution traps and the healthy battery**: a suggestive complaint over a
  quiet lab (D1 latent), a latency incident with a latent defect in plain sight, a
  degradation window that already closed.
- **Tier 3 — faint or dead surfaces**: process crash (logs only), low-rate chaos.

Coverage and the classes this lab cannot exercise: `eval/README.md`.

## Protocol

1. **Skills pinned.** All runs of a benchmark id use one commit of `skills/` and
   `hooks/`; the runner starts every investigation from a worktree of that HEAD. The
   commit is recorded in this file's results section when the table is published.
2. **Models.** v1: `claude-fable-5`, `claude-opus-5`, `claude-sonnet-5`; optional cheap-
   triage data point: `claude-haiku-4-5-20251001`. Subagents (lenses, judge) inherit the
   session model — the whole loop is one model per run.
3. **Repetition.** N = 3 per (fixture, model). Reported as pass rate over runs, never
   best-of.
4. **Fixed inputs.** The fixture's `complaint` verbatim through `/konan`; the skill's
   default budget (one triage round, at most 3 deep-dives per round, at most 2 rounds);
   `--permission-mode acceptEdits`; no other prompt text.
5. **Blinding and contamination control.** Fresh worktree per benchmark id with
   `journals/` emptied (no incident memory); `KONAN_EVAL_BLIND=1` makes the boundary hook
   deny the tracker (`gh`), reads under `eval/`, and the faultline checkout — mechanically,
   with denials counted by the tripwire; ground truth lives only in fixtures the session
   cannot read.
6. **Lab state.** `setup.lab: fresh` restarts faultline before the fixture (clean logs and
   counters); the `stage` list runs operator-side. Probabilistic fixtures state their
   restage rule (a user-visible failure must have landed) — checked before the run counts.
7. **Batching.** Runs draw from the same subscription pool as everything else; batches
   are sized with `--max-runs` and resumed by `--run-id`. A run that ends on a quota or
   rate-limit error is recorded and repeated; it does not count.
8. **Calibration.** Fixture matchers are calibrated on known-good journals where the
   mechanism is shared; first-cut matchers (stated in the fixture) may be calibrated
   after the first run of that fixture — as a committed fixture change, with the reason
   in the commit; re-scoring is deterministic and re-runs `eval/bench.py`.
9. **Fairness of the boundary.** The hook treats a `cd <session cwd> &&` prefix as
   transparent (a harness idiom); every other compound shape prompts and is auto-denied
   headless — recorded per run as denials, identical for every model.
10. **Coverage.** The runner pre-registers the plan of a run id in `plan.json` (the fixture
    ids and the repetitions) at its first invocation and refuses another plan under the
    same id. The table carries its coverage line per model — planned, completed, failed,
    missing, with the quota stops that explain a gap — at its head, rendered from that
    file and never from the live fixtures; a table with a missing count above zero is not
    published as complete.

## What the benchmark is for, beyond ranking

The table is also the instrument for optimization. Role-tiered configurations — a cheaper
model for the dedicated investigation work (lenses, deep-dives), a stronger one for
orchestration and the judge — are compared against the single-model rows on the same
fixtures; a configuration that holds the pass rate at lower tokens, cost, and quota share
becomes the recommended default, with the numbers. This is benchmark v2 (#65): the skill
reads a tiering config, the harness envelope attributes tokens and cost per model.

## Reproduce

```sh
# per model, tier-1 fixtures first, in batches
uv run eval/run.py --run-id bench-v1 --model claude-sonnet-5 --repeat 3 --max-runs 5
uv run eval/run.py --run-id bench-v1 --model claude-opus-5   --repeat 3 --max-runs 5
uv run eval/run.py --run-id bench-v1 --model claude-fable-5  --repeat 3 --max-runs 5
# … resume with the same --run-id until the coverage line says missing 0, then:
uv run eval/bench.py --runs eval/runs/bench-v1 -o eval/BENCHMARK-results.md

# bench-v2 (2026-11-02 to 2026-11-03): the ten fixtures in tier order, batches of ten, one model at a time
uv run eval/run.py --run-id bench-v2 --model claude-fable-5 --repeat 3 --max-runs 10 --fixtures \
  eval/scenarios/d1-zero-stock-product-page.yaml eval/scenarios/d2-null-price-order.yaml \
  eval/scenarios/chaos-error-rate.yaml eval/scenarios/chaos-latency.yaml eval/scenarios/healthy-baseline.yaml \
  eval/scenarios/t2-quiet-d1-suggestive-complaint.yaml eval/scenarios/t2-red-herring-latency-latent-d1.yaml \
  eval/scenarios/t2-healthy-after-chaos-window.yaml eval/scenarios/t3-crash-hard-down.yaml \
  eval/scenarios/t3-chaos-low-rate-intermittent.yaml
# … the same line with --model claude-sonnet-5 and --model claude-opus-5; resume with the same
# --run-id until the coverage line says missing 0 for each model, then:
uv run eval/bench.py --runs eval/runs/bench-v2 -o eval/BENCHMARK-results.md
```

## Limits (state them with the table)

- One small lab (faultline): four incident classes exercised; no load, no third party,
  no real database, no proxy tier.
- Fixtures are self-authored; the scorer measures what the fixtures encode.
- The lab is transparent by design — its gauge names the degradation switch; real
  stacks rarely do. Tier-1 ties across models are expected; the spread, if any, is in
  tiers 2–3 and in cost and time.
- N = 3 is variance-aware, not statistically strong; report counts, not significance.
- Blinding is mechanical for the tracker, fixtures, and the lab checkout; the model's
  prior knowledge of the public faultline repository cannot be controlled.

- **Dates:** 2026-08-19 → 2026-08-26, one operator machine, one lab instance.

  `eval/runs/bench-v1/` (committed alongside: every journal, sidecar and scorecard).
- **Regenerating it.** The committed table is the *pre-registered* scoring, and it
  reproduces byte-for-byte only at the commit that published it (`2a09171`). Re-scoring
  the same journals after the taxonomy fix collapses the two pass columns onto the
  class-agnostic value — Fable 47% → 73%, Opus 53% → 63%, Sonnet 17% → 50% — because the
  fix is exactly the widening the class-agnostic column was measuring. That delta is

  Which model leads depends on whether the class label counts. Opus leads the
  pre-registered rate; Fable leads once the ambiguous label is allowed its documented
  second value. Both orderings are stated because a benchmark that reports only the one
  it prefers is not a benchmark. Neither ordering is claimed as a capability ranking on

- **Headline, all tiers:** Opus leads the pre-registered pass rate (53% vs Fable 47% vs

  Fable and Opus cited evidence in 100% of runs, Sonnet in 80%. The cost column is
  API-equivalent and notional here: these runs were paid for in subscription quota.
- **Quota, measured (subscription is the meter):**
  - Investigations completed between quota stops (proxy for a 5-hour window):
    Sonnet ~24; Opus ~14–15; Fable ~11 (first window, shared with operator activity).
  - Weekly, measured via the operator's usage panel: the Fable-week meter moved
    75% → 86% across 5 consecutive Fable investigations — ≈2.2% of the weekly Fable
    quota per investigation, an upper bound because the orchestrating session shares
    the same meter. Consistent with the coarser ≈2.5% seen earlier over 16 runs.
  - Read that ceiling carefully: it was measured while a temporary +50% weekly-limit
    promotion was in effect (through 2026-08-31), which enlarges the denominator. The
    same consumption against the standard weekly limit is ≈3.3% per investigation —
    a ceiling nearer 30 Fable investigations per week than 45. Quota share is a
    property of a plan at a moment, not of the agent; the token medians are the
    portable number.
- **Failure modes observed (counted as failed runs, per protocol):**
  - Sonnet: ends the session asking the absent human to approve an operator command
    (`scripts/lab.sh status`) — all 6 of its failed runs are this, and no journal is
    produced. The boundary held; the model chose to stop. This is a real unattended-mode
    difference between models, not noise.
  - Fable and Opus: none — 30/30 journals each.
  - The one 30-minute timeout on record belongs to the invalidated first batch, not to
    this one; the runner now records a timeout as a failed run instead of crashing.
- **First batch invalidated and archived** (`eval/runs/bench-v1-invalid-logs/`): the
  runner's `lab: fresh` restarted the process but kept old log files, so later runs
  could read earlier runs' incidents; found by reading a journal that described the
  runner's own restarts. The protocol's blinding claim held only after the fix —
  stated here because a benchmark that hides its own invalid batch is not one.
- **Scoring findings filed during the run** (fixes are bench-v2, this table is scored
  as pre-registered): incident-class ambiguity for injected degradation (#63 — the
  class-agnostic column exists for exactly this), tripwires firing on negations
  (#64 — one Sonnet false-attribution is this artifact), and an under-calibrated
  `must_claim` on the tier-3 crash fixture (#75).
- **Tier 3 carries no model claim from this round.** Its near-zero pre-registered pass
  rate decomposes into the two scorer artifacts above, not into model capability:
  `t3-chaos-low-rate-intermittent` fails on the incident-class label (#63), and
  `t3-crash-hard-down` fails on one matcher, `must_claim no-restart-after`, which never
  matched in 8 of its 9 runs — all three Fable runs fail on that line alone, with the
  verdict, the citations and zero false attributions all correct. The signature is that
  class-agnostic pass is exactly 33% for all three models in tier 3, models that differ
  widely in every other tier: a fixture measuring itself. Tier 3 is re-run after #63 and
  #75 land, and no tier-3 number is quoted outside this file until then.
- **The strongest result is not a ranking.** `t2-quiet-d1-suggestive-complaint` — a
  dormant latent defect, a healthy system, and a complaint that implies an outage —
  caught every model at the same rate. Each held the line (`no-active-incident`) in
  exactly 1 of 3 runs; 5 of the 9 runs promoted a defect that was not firing into the
  cause of an incident that was not happening. Two things follow. It is
  model-independent, which makes it a finding about agentic investigators rather than
  about a vendor's model. And it is a stability result rather than a capability ceiling:
  same model, same fixture, same prompt, different verdict across repetitions — which is
  the empirical argument for N = 3, since a single run of this fixture would have
  reported either a clean pass or a clean failure and both would have been wrong.
